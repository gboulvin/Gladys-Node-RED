# Security policy

## Reporting a vulnerability

Please do **not** report a security problem in a public issue, pull request or
forum post.

Report it privately through GitHub instead: open the **Security** tab of this
repository, then **Report a vulnerability**.

No such button? Private reporting is not enabled yet: open an issue that only
asks the maintainers for a private contact, without any detail of the problem,
and send the report there.

Include, when you can:

- the version of the integration, of Node-RED and of Gladys;
- what an attacker can do, and the steps to reproduce it;
- the log lines that help (remove tokens, passwords and addresses first).

The fix ships as a new version of the integration, and the advisory is
published once users can update.

## Supported versions

Only the latest release receives security fixes: update the integration from
Gladys before reporting a problem.

## Security model

Node-RED can run arbitrary code: whoever reaches its editor controls the
container it runs in. The integration is built around that fact.

- **No editor without a password.** The Node-RED sub-container is declared
  `start: manual`: it is only started once the integration has written a
  `settings.js` enabling `adminAuth` with the configured credentials (8
  characters minimum). The password is stored in Gladys as a `secret` field
  and written to `settings.js` as a salted scrypt hash only.
- **HTTP endpoints of the flows** (`http in` nodes) require the same
  credentials by default (HTTP Basic). Users may turn this off for devices
  that cannot authenticate.
- **Event endpoint.** The integration listens on port 8080 for the events of
  the flows. The port is never published on the LAN, and every request must
  carry a random bearer token (`GLADYS_EVENT_TOKEN`) generated by the
  integration: the other integrations sharing the Gladys integration network
  cannot fire scene triggers.
- **Generated secrets** (Node-RED credential secret, event token, password
  salt) live in `/data/secrets.json` and `settings.js`, both owner-only
  (mode `0600`), never logged.
- **Containers.** The integration container runs read-only, as a non-root
  user, with no capability, on the network Gladys gives it. The Node-RED
  sub-container runs on a private network, with no capability, no privileged
  mode and no device access; its root filesystem is writable because
  Node-RED installs palette nodes. The editor port is the only one published
  on the LAN, chosen by Gladys.
- **Scene action "Send to a Node-RED flow"** only reaches the Node-RED
  container: the path is validated (no traversal, no other host).

Exposing the editor port outside the local network (port forwarding, reverse
proxy) is outside the supported setup: use a VPN or Gladys Plus.

## Scope

In scope: the code of this repository, the Docker image it publishes and the
Node-RED settings it generates.

Out of scope: Gladys Assistant itself (see its
[security policy](https://github.com/GladysAssistant/Gladys/security/policy)),
Node-RED and the third-party nodes users install (see the
[Node-RED security policy](https://github.com/node-red/node-red/security/policy)),
and the services the flows talk to.
